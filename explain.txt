What each part means
inception/

This is the root of your project. Everything is inside.

Makefile

This is the file the evaluator will use.

Later you will run:

make

and it will call Docker Compose.

Example goal:

docker compose -f srcs/docker-compose.yml up --build
README.md

General explanation of the project.

It must explain:

- what the project is
- how to run it
- Docker choices
- VM vs Docker
- secrets vs environment variables
- Docker network vs host network
- Docker volumes vs bind mounts
USER_DOC.md

Documentation for a user/admin.

It explains:

- how to start/stop the project
- how to access the website
- how to access WordPress admin
- where credentials are
- how to check containers are running
DEV_DOC.md

Documentation for a developer.

It explains:

- how to set up the environment
- how to build containers
- how to use docker compose
- how volumes work
- where data is stored
secrets/

This folder stores passwords locally.

Example later:

secrets/
├── db_password.txt
├── db_root_password.txt
└── credentials.txt

Important: this folder should not be pushed to Git.

Later you add it to .gitignore.

srcs/

This contains the real Docker project.

Think:

srcs = source files for the infrastructure
srcs/docker-compose.yml

This is the most important file.

It connects everything:

- mariadb container
- wordpress container
- nginx container
- volumes
- network
- ports
- restart policy
- env file

Docker Compose is like the boss that starts all containers together.

srcs/.env

This stores environment variables.

Example later:

DOMAIN_NAME=jjakupi.42.fr
MYSQL_DATABASE=wordpress
MYSQL_USER=wp_user

But passwords should ideally be in secrets/.

requirements/

This folder contains one folder per service.

requirements/
├── mariadb/
├── wordpress/
└── nginx/

Each service has:

Dockerfile = how to build image
conf/      = configuration files
tools/     = scripts
MariaDB folder
mariadb/
├── Dockerfile
├── conf/
└── tools/
mariadb/Dockerfile

Recipe to build your MariaDB image.

It will install:

mariadb-server
mariadb/conf/

Configuration files for MariaDB.

Example later:

my.cnf
mariadb/tools/

Scripts to initialize MariaDB.

Example later:

init_mariadb.sh

This script will create:

- database
- WordPress user
- root password
WordPress folder
wordpress/
├── Dockerfile
├── conf/
└── tools/
wordpress/Dockerfile

Recipe to build WordPress + PHP-FPM image.

It will install:

php-fpm
php-mysql
wordpress files
wp-cli maybe
wordpress/conf/

PHP-FPM config.

wordpress/tools/

Script to configure WordPress.

It will create:

wp-config.php
admin user
normal user
NGINX folder
nginx/
├── Dockerfile
├── conf/
└── tools/
nginx/Dockerfile

Recipe to build NGINX image.

It will install:

nginx
openssl
nginx/conf/

NGINX configuration.

It will say:

listen 443 ssl;
TLSv1.2 TLSv1.3 only;
send PHP requests to wordpress:9000;
nginx/tools/

Optional scripts.

For example, script to generate SSL certificate.

/home/jjakupi/data

This is not your code folder.

It is where Docker must store persistent data:

/home/jjakupi/data/
├── mariadb/
└── wordpress/

Meaning:

mariadb/   = database files
wordpress/ = website files

Even if containers are deleted, data stays there.

ADD është si COPY, por më special.

Mund të bëjë gjëra ekstra:

- mund të ekstraktojë tar files
- mund të përdorë URL\

Shell form
CMD echo "Hello $name"
ose:
ENTRYPOINT echo "Hello $name"
Kjo kalon përmes shell-it:
/bin/sh -c
Pra shell-i e interpreton $name.
Nëse ke environment variable:
name=Jetmir
mund të dalë:
Hello Jetmir
Exec form
CMD ["echo", "Hello $name"]
Kjo nuk kalon përmes shell-it.
Pra $name nuk zëvendësohet.
Del:
Hello $name
jo:
Hello Jetmir
Pse zakonisht përdorim exec form?
Sepse është më e pastër për Docker:
ENTRYPOINT ["/usr/local/bin/init_wordpress.sh"]

ENTRYPOINT ["/usr/local/bin/init_wordpress.sh"]:
Do të thotë:Kur container-i starton, gjithmonë ekzekuto këtë script
